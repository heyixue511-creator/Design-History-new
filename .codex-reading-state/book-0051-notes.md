## 第一章　设计系统而非页面（0—49345）

### 论证起点与历史叙事

- 本书以“页面”隐喻的历史惯性为问题起点：从泥板、卷轴到纸本及像素媒介，页面长期构成人类组织和消费文本的基本单位；万维网诞生于伯纳斯—李及 CERN 学者共享、链接文档的需要，因而网页、书签、分页等词汇既帮助早期用户理解新媒介，也把印刷时代的认知框架带进网络。
- Frost 并不否认页面隐喻曾有过渡价值，而是指出它已不足以描述流动、互动、相互依存的网络。项目工作量不能由“页面数”直接估算，而应由内容类型、布局、功能和组件的复杂度判断。三万页的大学网站可能只有少量内容类型与布局；首页也可能从一句标语到包含轮播、表单和第三方集成，复杂度悬殊。
- 从页面转向系统的历史解释以“模块化”为主线。作者把工业革命中的可互换零件和流水线、计算机科学的关注点分离与单一职责原则、YUI 和 jQuery UI 等早期界面库串联起来，说明模块化并非网络时代的新发明，而是在多设备环境中获得了更强的现实必要性。此处的福特叙述属于简化类比，适合作为概念导入，不宜作为工业设计史的充分证据。

### 战略、流程、内容、代码与视觉的模块化

- 作者批评组织每隔三至八年“推倒重来”的大型改版：骤变会让用户失去既有操作知识，而没有改变组织流程的改版很快又会陈旧。替代方案是最小可行产品、频繁发布、依反馈迭代；这要求组织结构与工作流共同变化，而不是只更换视觉外观。
- Frost 区分大写 Agile（特定软件开发方法及 Scrum、Lean 等框架）与小写 agile（拥抱变化、持续改进、保持灵活的一般愿望）。他主张根据组织结构、客户关系和人员条件寻找适合的流程，同时保留跨专业协作、尽早进入最终媒介、及早且频繁发布、把大任务分解为小组件等原则。
- 内容也应脱离固定页面。面对手机、阅读器、电视、车载屏幕等多种出口，组织需要结构化、可重组、可多渠道发布的内容块。Karen McGrane 的论述和 NPR 的 COPE 平台被用于说明“创建一次、到处发布”的内容基础设施。
- 代码侧以 JavaScript 的成熟以及 OOCSS、SMACSS、BEM 等 CSS 方法说明模块化架构；视觉侧则批评把大量 Photoshop 静态效果图当作最终网页的工作方式。静态工具仍适合探索 Andy Clarke 所说的“设计氛围”，Samantha Warren 的 style tiles 和 Dan Mall 的 element collages 将色彩、字体、质感及界面元素拆成小型探索物，以便在尚未锁定布局时讨论整体方向。

### 响应式界面、框架与定制系统

- Ethan Marcotte 的响应式网页设计以流式网格、弹性媒体和 CSS 媒体查询为三项基础，但作者强调，多设备设计并不只是“会伸缩的页面”；导航、灯箱、面包屑、轮播等每个组件都要面对屏幕尺寸、输入方式与环境变化。
- Foundation、Bootstrap 等前端框架把 HTML 模式、CSS 样式和交互脚本预组装，可提高原型、测试和发布速度；但通用框架也可能导致视觉同质化、下载无用代码、功能不足后大量定制，以及组织被迫接受外来的命名和结构。作者并非反对框架，而是借 Dave Rupert 的“为每个客户建立小型 Bootstrap”主张建立适合具体品牌和组织的活代码系统。

### 风格指南的类型与系统位置

- 设计系统以风格指南作为文档化与组织化基础。作者区分六类彼此关联的指南：
  - 品牌识别指南：标志、字体、色彩、信息与传播物料；
  - 设计语言指南：总体哲学、目标、原则及其应用，如 Google Material Design；
  - 声音与语调指南：声音保持品牌一致，语调随情境及读者感受变化，如 MailChimp；
  - 写作指南：为分布式内容生产规定语法、标点和基本写作原则；
  - 代码指南：统一 HTML、CSS、JavaScript 等代码约定；
  - 模式库：亦称前端风格指南、UI 库或组件库，是全书后续重点。
- 品牌识别相对稳定，设计语言可以随产品阶段变化；声音与语调、写作和代码规范又分别把抽象身份落实到具体生产。模式库因此不是孤立的组件清单，而是更大规范生态的界面层。

### 风格指南的价值、限制与治理问题

- 价值包括：以组件复用提高跨页面、跨渠道的一致性和可信度；建立跨专业共同词汇；向客户和利益相关者解释网站是系统而非页面集合；让各专业在同一资源中表达限制和关切；隔离组件以便测试；前期投入后加快后续设计开发；把分析、用户测试、A/B 测试及实践经验持续纳入长期知识基础。
- 作者把风格指南视为一种“共情工作流”：成员必须考虑局部决策对整体系统的影响，各专业也能看到彼此的要求。教育与文档同等重要，公开系统还可削弱部门以“特殊问题”为由反复要求定制方案的倾向。
- 主要困难包括：短期预算逻辑难以支持长期投入；建立系统本身耗时；模式库被当作主项目之外的附属品，首先被删减；缺少维护者、管理和执行机制；被误解为只供设计师或开发者使用；结构不友好、可见性不足；模式没有说明使用情境和影响范围；许多库只是松散模块堆积，缺少清晰方法。
- 作者把可访问性、性能、响应式和模式库并列为应嵌入工作流的基本原则，而非预算允许才添加的项目。这一表述体现全书由“制作组件”进一步转向“治理生产关系”的核心立场。

### 可用于教材的判断

- 本章最重要的史学用途，是说明 2010 年代响应式网络设计如何推动设计对象由固定页面转向可复用界面系统，并使品牌、内容、代码、组织流程与治理进入同一设计问题。
- 书中证据主要来自作者及合作者项目经验、行业案例和从业者引语，具有实践史与方法史价值，但不是严格的比较研究。书中关于技术普及度、效率、用户信任和历史先例的判断，教材引用时应以同期文档、项目档案或研究文献复核。

## 第二章　原子设计方法（49345—78256）

### 化学类比与五层结构

- Frost 从工业设计、建筑等领域的模块系统转向化学类比：自然界中的原子组成分子，分子进一步组成有机体；界面也可从有限的 HTML 元素出发形成更复杂的结构。作者明确承认这一自然科学说明经过简化，化学只是帮助理解层级关系的概念工具。
- 原子设计包含五个同时运作的层级，而非依次完成的五个步骤：
  - 原子（atoms）：不能在不丧失功能的情况下继续拆分的界面基础单位，如标签、输入框、按钮；尺寸、字体等固有属性影响其在系统中的使用；
  - 分子（molecules）：若干原子组成的简单功能单元，如标签、输入框、按钮合成搜索表单；以单一职责为原则，便于测试、复用和保持一致；
  - 有机体（organisms）：由原子、分子或其他有机体构成的相对复杂界面区段，如包含标志、主导航和搜索表单的页头，或重复产品卡片构成的商品网格；
  - 模板（templates）：把组件放入页面级布局，呈现内容结构而非最终内容，并规定图像尺寸、标题长度等约束；
  - 页面（pages）：以有代表性的真实内容填入模板，形成用户和利益相关者看到的具体实例，同时检验底层系统能否承受内容变化。
- 前三个名称提供由小到大的直观层级；到模板、页面时，作者主动停止延伸化学比喻，转而使用客户、管理者和同事更易理解的界面语言。这说明术语的功能是协作沟通，不是本体论断言。

### 内容结构、真实内容与系统韧性

- 模板与页面构成“内容骨架／具体内容”的区分。Mark Boulton 的观点是：可以在不知道具体文本的情况下设计，但不能在不知道内容结构的情况下创造良好体验；内容与设计也不是先后关系，而是相互塑造。
- 模板显示哪些组件共同工作以及内容参数，页面则以实际文本、图像和媒体检验系统。Time Inc. 首页模板及其索契冬奥会代表性内容被用作示范：标题长度、图片比例、栏目数量等一旦进入具体页面，便可能暴露组件尺度和排列问题。
- 购物车中一件或十件商品、新用户没有活动记录、标题四十或三百四十字符、管理员拥有额外按钮等变化，都在同一模板下产生不同页面状态。页面不是系统设计结束后的展示物，而是把失败反馈回分子、有机体和模板层的测试场。
- 原子设计的关键不是把内容从结构中彻底分离，而是在可区分的层级上观察二者如何相互限制。重复“人物块”在放入真实姓名后可能出现五行换行，迫使设计者回到更小层级修订规则。

### 部分与整体、抽象与具体

- 方法的主要优势是允许设计者在组件细节与最终界面之间往返。作者借 Frank Chimero 关于画家靠近画布落笔、退后观察整体的比喻，说明局部影响整体、整体也反过来规定局部。
- 因而不能先孤立完成全部按钮，再期待它们自然拼成统一界面。五个层级应并行使用：一面隔离检查组件的功能、可用性与视觉质量，一面在布局和真实内容中评估它们。
- 这一“部分—整体”的反馈结构，比原子、分子等名词本身更值得进入教材。它把设计系统呈现为持续验证的关系网络，而不是静态零件目录。

### 命名、组织适配与媒介边界

- “模块”“组件”“元素”“区段”等行业词汇缺少直观的大小关系，原子—分子—有机体便于建立共享层级；但作者反复强调，命名不是教条。GE 团队因同事难以接受原子术语，改用 Principles、Basics、Components、Templates、Features、Applications，只要能改善组织沟通即可。
- “Atomic Design”可作为向利益相关者解释模块化的简短标签，但组织应根据自身语汇调整分类，而非服从一种外部命名体系。
- 方法诞生于 Web，却不等同于 CSS 或 JavaScript 架构。作者以 Instagram 原生移动应用为例，把图标与文本视为原子、导航和操作栏视为分子、照片卡片视为有机体、信息流骨架视为模板、真实用户内容视为页面，从而把适用范围界定为一般用户界面。

### 可用于教材的判断

- 本章可作为 2010 年代组件化界面设计的原始方法文献，重点应放在五层模型、真实内容测试、部分—整体反馈及组织语汇适配，而不应把自然科学类比写成设计发展的必然规律。
- Time Inc.、GE、Instagram 等例子均为方法演示，不能仅凭本书推导企业成效或普遍采纳程度；其中冬奥会内容只是页面样本，并非奥运视觉识别或公共建筑研究材料。

## 第三章　工具与有效模式库（78256—112628）

### Pattern Lab 的定位

- 模式库是汇集界面组件的中央枢纽；Pattern Lab 是作者与 Dave Olsen、Brian Muenzenmeyer 共同维护的开源项目。本章虽以它为观察镜头，但作者强调目标是提炼有效模式库的属性，不是把某一工具规定为唯一答案。
- Pattern Lab 是用于构建设计系统的静态站点生成器、模式文档与注释工具、模式起始套件；它不是 Bootstrap 或 Foundation 一类提供现成视觉方案的 UI 框架，不依赖特定语言、库和样式，也不替代正式内容管理系统。
- 默认界面刻意简朴，以免使用者把示例误认为推荐风格。PHP 或 Node.js 负责生成，但输出为后端无关的 HTML、CSS、JavaScript；技术选择应服从组织现有基础设施和协作方式。

### 嵌套、单一来源与动态数据

- Pattern Lab 以俄罗斯套娃解释嵌套：原子包含于分子，分子进入有机体，有机体进入模板。Mustache 的 include 语法把小模式引用到大模式，使修改一处即可更新所有使用位置，落实 DRY（不要重复自己）原则。
- Time Inc. 案例从缩略图、标题和摘要组成的内容块，到由标志、导航和搜索组成的页头，再到首页模板，演示同一套模式如何在不同尺度嵌套。模板可给同一组件实例命名，以便在页面层替换数据。
- JSON、YAML、Markdown 等数据文件使结构与具体内容分开。默认数据定义占位内容，页面同名数据文件覆盖标题、图像等值；变量、数组和条件还可改变组件状态。这一机制一面保持结构复用，一面让真实内容参与测试。
- “伪模式”（pseudo-pattern）继承既有页面数据，仅覆盖或追加少量变量。例如管理员仪表盘把 `isAdmin` 设为真，便显示编辑、删除操作。该机制用于同时设计最佳、最差及中间状态，纠正静态效果图只表现姓名短、头像完美、栏目齐整等理想情形的倾向。
- 数据分离还能形成轻量内容管理环境，给后端整合提供蓝图，并允许写作者、内容人员和非开发者安全修改文案、图像，使界面系统不被前端开发者垄断。作者仍明确 Pattern Lab 不等于生产 CMS。

### 响应式测试、代码与活文档

- 流动组件应能适应全幅、正文和侧栏等不同容器。作者提到当时仍在开发的 container queries，并用 `ish.` 工具随机给出 small-ish、medium-ish、large-ish 视口，避免团队只在 320、480、768 像素等流行设备尺寸上测试。该书写于 2016 年，关于容器查询的技术状态具有明确时代性，教材不能当作当前状态照录。
- 代码视图应展示组织真正需要的 HTML、模板、CSS 或 JavaScript。Salesforce Lightning 展示 HTML 与 SCSS；Lonely Planet 的 Rizzo 则直接提供组件引用代码，使模式库与生产环境共享单一代码来源。作者将二者完全同步称为模式库的理想状态。
- 传统线框和规格 PDF 往往在上线后被丢弃；有效模式库把定义、用法、可访问性、性能、美学等跨专业说明放在运行中的组件旁。Pattern Lab 可用同名 Markdown 添加模式说明，也可把编号注释直接挂接到完整界面的相应元素。
- “模式谱系”（pattern lineage）同时显示一个组件由哪些较小模式构成、又被哪些更大模式使用。修改图像尺寸或添加元素时，团队由此识别必须重新测试的位置；谱系也暴露重复或几乎不用的模式，支持清理。

### 工具选择原则与史料限度

- 作者总结的有效模式库能力包括：说明与注释、相关代码展示、全分辨率范围查看、组件状态变化、真实数据注入、组成关系及使用位置追踪。这些能力比具体软件品牌更具有方法史意义。
- 全章最终把工具问题重新导向文化、流程和工作流：工具只能把关系显现并支持协作，不能自动建立或维护系统。教材可据此讨论 2010 年代设计工具由成图工具转向“活文档＋代码＋治理基础设施”的变化。
- 版本性信息必须注明：Mustache、Pattern Lab、`ish.`、当时的 container queries 状态及企业模式库均属于作者写作时的技术现场。若教材讨论其后演变，应另查官方版本档案。

## 第四章　原子化工作流（112628—189674）

### 人、组织承诺与系统启动

- 作者把技术和工具置于“人”的条件之下：有效设计系统依赖持续协作与沟通，是组织整体工程。新设计、改版、平台迁移可为模式库提供经费和项目入口，也可单独立项；最佳启动时间被概括为“现在”。
- 对管理者推介时，Frost 建议把一致性、生产率、共享词汇、文档、测试和长期适应性转译为时间、成本、转化、风险及用户覆盖。此种商业论证反映实践者争取组织资源的策略，但“设计系统必然增加转化／避免诉讼”等说法在教材中必须降格为作者主张，不能当作已验证因果关系。
- “活的”系统应把 A/B 测试、性能优化等新经验继续纳入规则。组织承诺不能只停留在赞同概念，还需配置实际时间、资金与人员。

### 界面清查：由隐性差异到共同问题

- “界面清单／界面审计”（interface inventory/audit）借鉴内容清查，通过截图、分类列出界面的独特组件，而非截取每个重复实例。它既是描述现状的材料，也是让非设计人员直观看到按钮、表单、颜色等不一致性的组织动员工具。
- 作者要求用户体验、视觉、前后端、文案、内容策略、项目管理、业务、质量保证等代表共同参与，以便差异不再只是某个设计师的私人发现，并在讨论中形成跨专业词汇。参与者采用统一软件，在限定的三十至九十分钟内分别搜集一类模式。
- 建议清查范围包括全局元素、导航、图像、图标、表单、按钮、标题、内容块、列表、交互组件、音视频、第三方组件、广告、提示状态、色彩与动画。范围需按组织情况增删，并深入客服、FAQ、尺寸说明、404、法律条款等不受首页团队重视的区域，因为用户把品牌体验理解为一个整体。
- 各组展示发现，讨论同一组件的不同命名；负责人合并为总文档，再由小型跨专业团队补漏，决定保留、删除、合并哪些模式，统一名称并转化为活模式库。清查的结果包括识别冗余、争取支持、估算工作量和奠定共享语言。
- “先做后请示”一节主张在管理者拒绝时仍把设计系统像性能、可访问性、响应式一样嵌入专业流程，甚至暂不告知利益相关者。它反映作者的专业自治立场，同时也存在治理风险：在教材中应与项目授权、透明度、责任及资源边界并置讨论，不宜直接规范化。

### 重定义数字设计与批评瀑布流程

- Frost 认为印刷传统使网络长期被当作静态画面销售，视觉外观压倒速度、屏幕、网络、交互、人体工学、可用性、可访问性、情境和偏好。多设备环境要求把包容性、弹性布局、性能、渐进增强及面向未来的适应性纳入“好设计”的定义。
- 作者承认印刷设计本身复杂，并非简单贬低印刷；论点在于双向互动网络增加了不同维度。这里的“纸媒／数字媒介”对比仍有二元化倾向，教材应避免把两者写成单线替代关系。
- 被批评的瀑布流程是：用户体验人员完成庞大线框 PDF，视觉设计师制作静态稿并多轮审批，前端最后才接到定稿，被迫在已批准的桌面画面上补响应式布局、组件状态和交互，最终造成预算延误与专业冲突。
- 数字媒介修改成本相对较低，可迅速测试假设，因而研究、信息架构、视觉和开发不应按严格交接次序排队。各专业投入强度可随阶段增减，但始终保留咨询关系。作者以协作图替代流水线图，强调并行工作和反馈回路。
- 这种论述不能理解为数字修改“没有成本”，也不能把建筑、制造、印刷笼统归为瀑布。它是一位 Web 从业者针对特定项目组织的批评性描述。

### 前端开发作为设计与迭代媒介

- HTML、CSS 和呈现层 JavaScript 直接构造界面，前端开发不应因“代码”身份被简单归入后端工程并与设计隔离。尽早进入浏览器，利益相关者才能评价弹性、网络影响、交互、运动、人体工学、色彩与文字渲染、像素密度、滚动、设备差异及用户偏好。
- 作者没有要求全部在浏览器内设计；静态图可表现审美方向，运行原型可表现媒介行为。选择工具的标准是当前要表达和检验的问题。
- 迭代被比作石雕：先形成粗略整体，再逐区细化，持续退后观察局部对整体的影响。项目要让管理者适应半成品与滚动更新，而非只看精致的“大揭幕”。沟通、短反馈回路与跨专业协作承担协调模糊过程的作用。

### 建立内容、显示与视觉方向

- 在高保真制作前，团队先确定广义方向。用户体验人员可用低保真草图、基础 HTML 或项目清单说明屏幕有哪些内容及大致顺序；移动优先利用小屏约束迫使团队确认核心内容和层级。TechCrunch 的“展示岛”等手势式显示模式刻意不预设最终布局或功能。
- 表格亦可按模板列出显示模式、所含内容、顺序、用途和示例；纵读第一列近似移动端内容顺序。其价值在于先回答“有什么、以何种总体次序出现”，避免过早固化技术和布局。
- 视觉方向采用三种渐进工具：
  - 二十秒直觉测试：向利益相关者快速展示二十至三十个本行业及跨行业网站，按喜恶评分，再讨论最低、最高和分歧最大者，以显现字体、色彩、密度、布局、插图和气质偏好；
  - 风格拼贴（style tiles）：介于情绪板与完整效果图之间，探索色彩、字体、质感、图标及“设计氛围”，不承担完整布局；
  - 元素拼贴（element collages）：把上述气质用于实际界面组件，但仍不构成完整页面，以较低成本让利益相关者讨论方向。
- 三种方法不是保证形成客观审美共识的实验，而是减少过早高保真投入、把偏好外化为可讨论材料的协作技术。

### 从准备工作到运行界面

- 作者以餐厅备菜厨师比喻前端人员：从项目首日设置代码库、服务器、CMS 和工具，并为页头、页脚、登录、购物车等可预见模式搭建粗略语义结构。这样，开发者可与设计师同期验证信息架构、源代码顺序和布局，而不是在设计结束后被动生产。
- 各专业并行但不隔离：用户体验建立内容层级，视觉设计开展审美探索，前端建立依赖、模板和结构标记；想法可通过纸巾草图、CodePen 原型、Sketch、Balsamiq、After Effects 等任一适当媒介表达。
- TechCrunch 页头案例展示循环：Dan Mall 的元素拼贴用于讨论审美、层级和功能；Frost 同期在 Pattern Lab 中建立灰度 HTML 原型，现场演示交互与分辨率变化；团队和客户共同调整信息架构、布局、功能和细节；页头又通过 include 同时出现在各模板，使局部始终接受整体情境检验。
- 半成品页面中某些模式可能成熟、另一些仍粗糙；作者认为传达真实进度优于制造虚假的完整感。完整静态稿仍有用途：当利益相关者已接受总体气质而需要观察整体时，可制作少量页面稿作为讨论假设，随后把小调整移入浏览器。
- “在浏览器中设计”被改写为“在浏览器中决定”：静态稿不能确认动态数据、交互、性能、人体工学和浏览器差异，转入最终媒介后才可检验。设计师可继续制作局部静态稿，前端迭代运行代码，形成往返循环。
- 随组件逐渐完成，引用它们的模板也同步成熟，新模板越来越多地变成组合既有模式。上线阶段，各专业共同检验流程、视觉、浏览器设备、CMS 整合和文档，最终交付网站与可继续维护的系统。

### 教材转化

- 本章可支撑“数字设计工作流的组织史”而不仅是工具史：对象从页面变为组件关系，成果从最终画面扩展到代码、文档、分类、词汇与协作制度，设计师、开发者、内容人员、管理者的边界随之重组。
- United、TechCrunch、Entertainment Weekly、匹兹堡食物银行等案例多为作者亲历或方法示范，适合说明从业者如何叙述实践；其效率、成本及用户效果仍需独立证据。

## 第五章　维护设计系统（189674—249470）

### 从交付物到长期产品

- 本章以 Nathan Curtis 对“风格指南交付物”和“设计系统产品”的区分开篇：前者可能像 PSD、PDF 一样成为不再更新的静态遗留物，后者则需要经费、路线图、待办清单和持续服务的生态。
- 如果模式库与实际产品脱节，团队会回到局部修补和临时修改，原有系统逐步被侵蚀。作者主张把应用层发现的问题先提升到系统层判断：例如某页面的定制下拉菜单表现不佳，需检查同一模式在其他位置是否也应整体修改。
- 这种“友好摩擦”让功能请求、试验结论和修复在进入产品前接受整体审查，抑制一次性例外；同时也需要警惕过度中央化拖慢必要的局部响应。
- 数字系统没有一次性“完成”状态。客户服务式项目和内部专项都容易在交付后转向下一件工作，而设计系统应被理解为服务其他产品、随媒介、用户和业务改变的长期产品。

### 正式化、团队与角色关系

- 长期运行的条件被概括为：正式、可适应、可维护、跨专业、可亲近、可见、范围更大、情境无关又提供情境、能够延续。
- 正式化路径是“先做出东西—证明有用—转为正式项目”：以试点建立可见的模式库，借多专业成员说明其价值，再争取高层批准、专职或兼职人员、治理计划和产品路线图。草根起步并不等于可长期依赖无偿加班；教材应把作者的“周末做出雏形”置于组织劳动与资源分配问题中审视。
- 作者区分系统制作者（makers）和使用者（users）。制作者维护、批准和治理系统，掌握生态整体；使用者把模式用于具体应用，提供现场反馈。Salesforce 的 Jina Bolton 将关系概括为设计系统影响产品设计，产品设计也反向影响系统。
- 大型组织可设置专职团队，小组织由有经验且有执行权的成员兼任；外部机构能提供比较视角和启动建议，但难以替代内部长期所有权。使用者可能是同一团队、其他产品组、初级设计开发人员、合作机构或第三方。
- 跨专业并非要求每个人始终直接编辑系统。用户体验、视觉和前端通常承担日常制作，后端、内容、产品、项目管理和管理层提供架构、业务与应用反馈。系统把响应式、可访问性、性能等原则规模化，但这不意味着系统能消除个体判断或自动保证质量。

### 适应性与变更治理

- 把设计系统视为不可改变的“唯一真理”会迫使使用者绕开系统。治理计划需回答：现有模式不适合时修改、替换还是新建；新请求如何处理；旧模式如何退役；错误由谁修复；谁批准、写文档、改代码和部署；变化如何通知使用者。
- 日常渠道、办公时间、问题跟踪和定期“系统状态”会议把制作者、使用者和关键利益相关者保持在同一反馈回路。Canonical 的 Vanilla 决策树被用来说明新模式从提议到正式接纳可有明示流程。
- 变更有三类：
  - 修改：因功能、错误、视觉、性能、可访问性、重构或用户体验规范更新而调整；
  - 增加：应用出现真实缺口时新建，但先判断是否一次性需求，避免模式库无限膨胀；
  - 删除：因效果差、技术与行业变化、长期不用或负面反馈而弃用，并提前标记、提供替代，避免突然破坏依赖它的产品。Salesforce 的 Sass Deprecate 是示例。

### 技术同步与组织条件

- 作者称模式库和生产应用自动同步为“圣杯”：模式只维护一个来源，修改后文档和所有应用共同更新。Lonely Planet 的 Rizzo 通过模式 API 同时供应生产环境和模式库，是主要案例。
- 实现同步存在技术梯度：从人工复制前端代码，到把模式库直接嵌入生产环境。CSS 和呈现层 JavaScript 可经 CDN 及版本化 URL 分发，标记语言因与后端逻辑交织更难共享。
- Mustache、Handlebars、Twig、Underscore、Jade、Nunjucks 等模板语言把结构与数据分开，可成为模式库和应用间的桥梁。Phase2 以 Pattern Lab、Drupal 共同支持 Twig，再通过 Drupal 组件库模块共享同一模板。
- “圣杯”也受组织结构限制。多平台、跨国、自治或高度分散机构未必能集中同步；本书以美国联邦政府 Draft U.S. Web Design Standards 为例，指出它更现实地提供可下载的标记和样式。此处涉及政府识别，但不是国徽、旗帜或地图材料；教材若使用，应仅讨论公共数字服务标准与分散治理。
- 技术集中度不应被当作成熟度的唯一尺度。即使不能自动同步，一组核心模式、文档和原则仍可逐步建立共同基础。

### 跨专业文档、传播、培训与公共性

- 风格指南不应只是开发者代码仓库。作者以电商首页轮播说明，一个组件同时涉及商品与编辑选择、文案长度、摄影和小屏可读性、交互、响应式／可访问性／性能、后端整合；模式文档可把这些不同责任集中呈现。
- 指南外壳需好看、易导航并说明用途和受众，但先建立有用系统，再逐步改善“家”。可亲近性被视为扩大非开发者参与和组织认同的条件。
- 可见性依赖持续“推广”和变更传播：内部博客、讨论频道、变更日志、路线图、成功案例、使用提示，以及在 Slack、Basecamp、GitHub、Wiki、邮件或内网中的自动通知。Shyp 的 pull request 自动通知设计频道是例子。
- 文档不足以替代学习。培训可通过结对、工作坊、网络讲座、教程和新员工入职；支持可通过问题跟踪、办公时间、聊天、论坛和主动访谈。使用者还可提交建议与 pull request、参与访谈、圆桌、调查和定期会议，从消费者转为共同贡献者。
- 作者主张公开风格指南，以提高可达性、问责和招聘吸引力，反对把通用 UI 模式视为商业秘密；Styleguides.io、Salesforce 案例支撑这一行业立场。公开策略仍需服从安全、隐私和组织政策，书中没有系统讨论这些例外。
- “做得更大”指把品牌、声音与语调、代码、设计原则、写作指南以及 Web、iOS、Android 的共同和差异模式汇入一个中心，如 Intuit Harmony。中心化提高发现性，但教材可进一步追问谁有权定义规范以及地方差异如何保留。

### 命名、语境与持续价值

- 模式名称应尽量根据结构而非所在页面或当前内容命名：`homepage carousel` 改为 `carousel`，`product card` 改为 `card`，扩大可移植性。界面清查及模糊内容的命名练习帮助团队暂时脱离具体语境观察结构。
- “情境无关”不等于“没有使用情境”。模式库还应以截图、视频、详细用法及模式谱系说明组件如何使用、由什么组成、出现在哪里，从而支持正确采用和变更后的质量检查。Material Design 与 Pattern Lab 分别示范丰富用法文档和谱系。
- 作者以汽车贬值／葡萄酒增值比喻维护差异，最终再次强调长期经费、治理、部署、传播、跨专业文档、可见性、适当命名和上下文说明。

### 教材转化

- 本章是本书最适合设计学理论教学的部分：它把“设计系统”从形式一致性提升为制度、劳动分工、知识管理、技术架构和组织权力共同构成的社会技术系统，可与 SCOT、基础设施研究和组织设计结合。
- 书中对“最佳实践”“效率”“质量控制”“公开必然有益”的肯定具有强烈倡议性质。教材应保留行动者语言，同时以企业档案、维护数据、失败案例、无障碍评估及不同组织形态进行对照。

## 全书综合判断

- 核心命题：响应式、多设备和动态内容环境使“页面”不足以作为数字设计的主要生产单位；组织应把界面理解为由可复用模式构成、经真实内容测试、由跨专业团队持续治理的系统。
- 五章论证形成递进链：媒介条件说明为何需要系统；五层模型提供观察结构；Pattern Lab 显示结构如何成为运行工具；原子化工作流重组专业协作；维护章把成果转化为长期产品和制度。
- 写作方式以第一人称经验、幽默类比、同业引语、项目截图和操作清单推进，理论密度低于实践可操作性。它能还原 2010 年代 Web 设计共同体如何命名问题、争取资源和建立专业身份，但不能独立证明历史因果、采用规模或商业成效。
- 在《现当代设计史》中，本书宜作为“响应式 Web、组件化界面与设计系统治理”专题的核心一手／行动者文献，同时与同期官方技术标准、企业模式库版本档案、开源仓库记录、组织研究、用户研究及批判性设计研究互证。
