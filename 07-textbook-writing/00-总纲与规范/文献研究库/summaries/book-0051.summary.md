# 核心问题与全书总论

Frost 的核心问题是：当 Web 已成为流动、互动、多设备、由动态内容驱动的媒介时，为什么设计与项目管理仍以固定“页面”为主要单位？他的答案是，页面隐喻虽帮助早期用户理解万维网，却把印刷时代的生产逻辑延续到数字媒介；项目应按内容类型、功能与组件而非页面数量估算和构造。

全书以“模块化”贯通战略、内容、视觉、代码、工具、协作和维护。原子设计不是一种视觉风格，而是同时观察部分与整体的界面系统方法：原子、分子、有机体、模板、页面五个层级并行工作；真实内容和不同状态不断检验底层模式；模式库则把代码、文档、状态、依赖和使用情境集中为可运行基础设施。

设计系统也不是交付完成后即可封存的风格指南。它是需要经费、路线图、人员、变更程序、培训和传播的长期产品。由此，设计对象从单个画面扩展为代码、分类、命名、文档、专业协作、组织决策和技术架构共同组成的社会技术系统。

五章形成明确递进：

1. 多设备与动态内容环境说明为何要从页面转向系统；
2. 五层模型提供构造和观察界面的共同语言；
3. Pattern Lab 展示模型如何落实为活代码、数据和文档工具；
4. 原子化工作流重组用户体验、视觉、前端、内容和管理者之间的关系；
5. 维护与治理使系统从项目交付物转化为长期组织产品。

## 第一章　设计系统而非页面（字符 5270—49345）

### 页面隐喻及其限度

- 页面从泥板、卷轴、纸本延续到像素媒介；万维网诞生于伯纳斯—李和 CERN 学者共享、链接文档的需求，因此网页、书签、分页等词汇深植网络语言。
- Frost 承认页面隐喻曾降低新媒介的理解门槛，但反对继续用“几页网站”估算设计。三万页大学网站可能只有三种内容类型和两种布局；首页则可能因表单、轮播、第三方集成而从数小时到数月不等。
- 设计工作量应由页面中功能、内容类型、布局和组件决定，而非页面总数。

### 模块化的多重来源

- 作者用可互换零件、福特流水线、计算机科学的关注点分离和单一职责原则，说明模块化早于 Web。
- YUI、jQuery UI 等组件库使模块化进入早期 Web 工具；响应式、多设备环境进一步提高了把复杂责任拆成小单元的必要性。
- 工业革命和福特的叙述高度概括，只能视为方法类比，不能替代工业设计史证据。

### 战略、内容、代码和视觉

- 作者批评每三至八年推倒重来的大型改版：骤变使用户失去既有操作知识，而未改变组织流程的新界面也会迅速陈旧。
- 替代方式是最小可行产品、频繁发布和持续迭代。Frost 区分大写 Agile 的特定方法体系与小写 agile 的一般灵活性，主张按组织约束采用跨专业、早进入最终媒介和拆分任务等原则。
- 内容应被结构化为可重组的块，以适配手机、阅读器、电视、车载屏幕等多种出口。Karen McGrane 的论述与 NPR COPE 平台说明“一次创建、多处发布”的内容基础设施。
- JavaScript 的模块模式及 OOCSS、SMACSS、BEM 说明代码架构变化；style tiles 和 element collages 则说明视觉设计从大量完整静态稿转向色彩、字体、质感和组件的局部探索。

### 响应式设计与通用框架

- Ethan Marcotte 的响应式网页设计以流式网格、弹性媒体和媒体查询为基础，但每个导航、灯箱、面包屑、轮播都仍需处理不同屏幕和输入方式。
- Foundation、Bootstrap 提供预装 HTML、CSS 和 JavaScript，提升原型和测试速度，却也可能造成视觉同质化、无用代码、能力不足后的大量定制，以及外来命名与组织语汇冲突。
- 作者由此主张 Dave Rupert 所说的“为每个客户建立小型 Bootstrap”：保留框架的系统性，但为具体品牌和业务定制。

### 风格指南生态

- 品牌识别指南规定标志、字体、色彩、信息和物料；
- 设计语言指南说明总体哲学、目标、原则及应用，如 Material Design；
- 声音与语调指南规定稳定的品牌声音及随情境变化的语调，如 MailChimp；
- 写作指南统一内容生产；
- 代码指南统一实现约定；
- 模式库集中前端／UI 组件，是本书主要对象。
- 设计语言可以更换，而品牌识别相对稳定；语调、写作、代码和模式库分别把抽象身份落实到生产环节。

### 价值与困难

- 价值：一致性、可信度、共享词汇、教育、跨专业协作、隔离测试、提高后续开发速度、积累分析与测试知识。
- 困难：短期预算、建立成本、被当作附属项目、缺少维护与执行、受众局限、结构不友好、缺少使用情境、模式分类松散。
- 作者把可访问性、性能、响应式和模式库视为应嵌入流程的基本条件，而非事后添加项目。

## 第二章　原子设计方法（字符 49345—78256）

### 五个并行层级

- 原子：不能在不丧失功能的情况下继续拆分的界面单位，如标签、输入框、按钮；
- 分子：若干原子组成的简单功能单元，如搜索表单，以单一职责提高测试和复用；
- 有机体：由原子、分子或其他有机体组成的界面区段，如页头和商品网格；
- 模板：把组件放入页面级布局，显示内容骨架、图像尺度和字符长度等约束；
- 页面：把有代表性的真实内容放入模板，显示具体实例和各种状态，并检验系统韧性。

### 方法不是线性步骤

- 五层不是“先做完原子再逐级向上”的流程，而是同时观察抽象与具体、局部与整体的心智模型。
- 作者借 Frank Chimero 的画家比喻：靠近画布落笔，再退后观察局部如何改变整体。
- 分离结构与数据不等于切断关系。姓名长度、图像比例、购物车数量、权限和新用户状态会迫使团队回到更小模式修订参数。

### 模板、页面与真实内容

- Mark Boulton 的观点是：可以暂时不知道具体内容，却不能不知道内容结构；内容与设计相互改变。
- Time Inc. 首页模板以索契冬奥会代表性内容进行页面测试，检验标题、图像、栏目和组件关系。
- 一件或十件商品、四十或三百四十字符标题、普通用户或管理员等差异说明同一模板需呈现多种页面状态。

### 命名与适配

- 原子—分子—有机体的优势是名称本身暗示层级；“模块”“组件”等词未必有共同大小关系。
- GE 团队因内部成员不接受化学术语，改用 Principles、Basics、Components、Templates、Features、Applications。
- 作者明确表示原子设计不是教条，组织应选择最能促进沟通的分类。

### 媒介范围

- 原子设计诞生于 Web，却不是 CSS 或 JavaScript 架构。
- Instagram 原生应用案例把图标、文本、头像视为原子，把导航和操作栏视为分子，把照片卡片视为有机体，把信息流骨架和真实数据分别视为模板与页面，说明方法适用于一般用户界面。

## 第三章　工具与有效模式库（字符 78256—112628）

### Pattern Lab 的边界

- Pattern Lab 由 Brad Frost、Dave Olsen、Brian Muenzenmeyer 维护，是静态站点生成器、模式文档与注释工具和起始套件。
- 它不是 Bootstrap 一类 UI 框架，不规定视觉、命名、代码结构或库，也不替代正式 CMS。
- PHP 或 Node.js 负责生成，输出为后端无关的 HTML、CSS、JavaScript；默认外观刻意简朴，以免被误认为推荐样式。

### 嵌套、DRY 与数据

- 俄罗斯套娃式 include 让原子进入分子、分子进入有机体、有机体进入模板；Mustache 引用使修改一处即可更新全部使用位置。
- Time Inc. 案例从内容块、页头到首页模板，显示小模式如何组合为布局。
- JSON、YAML、Markdown 等数据文件定义默认内容，页面数据覆盖标题、图像、数组和条件变量，使真实内容进入结构测试。
- 伪模式继承原有数据并覆盖少量变量，如 `dashboard~admin.json` 只把 `isAdmin` 设为真，就显示管理员操作。
- 动态数据让团队设计无头像、长标题、零评论、多层评论等非理想状态；也为后端整合提供蓝图，并允许文案与内容人员直接参与。

### 响应式、代码和文档

- `ish.` 随机给出 small-ish、medium-ish、large-ish 视口，避免团队只在流行设备宽度上测试，并教育客户理解连续分辨率。
- 书中 container queries 尚处开发阶段，明确反映 2016 年技术现场；不得作为当前技术状态直接引用。
- 代码视图可展示 HTML、模板、CSS、JavaScript。Salesforce Lightning 展示 HTML 与 SCSS；Lonely Planet Rizzo 提供组件引用代码。
- 同名 Markdown 说明和界面注释把定义、用法、可访问性、性能及审美考虑放在运行组件旁，替代上线后失效的规格 PDF。
- 模式谱系显示某组件包含哪些小模式、又被哪些大模式使用，帮助识别变更影响、测试范围、重复模式和低使用模式。

### 有效模式库的通用属性

- 模式说明和注释；
- 与组织相关的代码展示；
- 全分辨率范围查看；
- 状态与变化；
- 真实数据注入；
- 组成关系和使用位置；
- 工具适配组织技术、流程和文化，而非反过来。

## 第四章　原子化工作流（字符 112628—189674）

### 组织动员与商业论证

- 设计系统依赖人际协作和沟通；新设计、改版、平台迁移可成为启动机会，也可专门立项。
- 对管理者推介时，作者把一致性、速度、测试与长期适应性转译为时间、金钱、转化和风险。
- “设计系统会增加转化、避免诉讼”等是倡议性主张，教材需另找数据验证。

### 界面清查

- 界面清单仿照内容清查，以截图收集所有独特组件而非每一实例。
- 用户体验、视觉、前后端、文案、内容策略、项目管理、业务和质量保证共同参与，分别清查全局元素、导航、图像、图标、表单、按钮、标题、内容块、列表、交互、媒体、第三方组件、广告、提示、色彩和动画。
- 清查范围应包括客服、FAQ、404、法律条款等非核心页面，因为用户不按组织部门划分体验。
- 分组展示使同一模式的不同名称显露；合并总文档后，团队决定保留、删除、合并、命名和转入模式库的方案。
- 作用包括揭示冗余、争取组织支持、界定工作范围和建立共同语汇。

### 专业自治的争议

- 当管理者拒绝时，作者建议“先做后请示”，把系统像性能、可访问性、响应式一样内置于专业过程。
- 这反映 Web 设计师争取专业自治的立场，但也涉及授权、透明度、无偿劳动和责任问题；教材不能将其直接写成规范。

### 重定义数字设计

- 数字设计不只处理视觉外观，还包括速度、屏幕、网络、技术能力、形态、人体工学、可用性、可访问性、情境和用户偏好。
- 作者承认印刷设计本身复杂，但认为静态媒介流程不应直接套用于双向、互动和多设备的 Web。
- 包容性、弹性布局、性能、渐进增强和未来适应性被纳入设计质量。

### 瀑布流程批评与前端身份

- 用户体验人员交付完整线框 PDF，视觉设计师制作并审批静态稿，前端最后接手的线性流程，会让响应式、状态、交互和技术限制太晚出现。
- 研究、信息架构、视觉和开发应并行推进，投入强度虽随阶段变化，各专业仍持续咨询。
- HTML、CSS 和呈现层 JavaScript 直接构造用户界面，因此前端开发属于设计过程，而非单纯后端工程。
- 尽早进入浏览器，可检验弹性、网络、交互、运动、人体工学、渲染、像素密度、滚动、设备和用户偏好。

### 低保真方向与视觉工具

- 用户体验人员先用低保真草图、基础 HTML 或表格确定内容、层级和大致顺序；移动优先利用小屏约束突出核心信息。
- 二十秒直觉测试用二十至三十个网站快速显现利益相关者对字体、色彩、密度、布局、插图和气质的偏好。
- Style tiles 探索色彩、字体、质感和图标，不预设布局。
- Element collages 把视觉气质用于实际组件，却仍不形成完整页面。
- 这些都是讨论工具，不是客观审美测量方法。

### 前端“备菜厨师”与浏览器迭代

- 前端人员从第一天设置代码库、服务器、CMS，并为页头、页脚、登录、购物车等可预见模式建立粗略结构。
- TechCrunch 页头从 Dan Mall 的元素拼贴与 Frost 的灰度 HTML 原型同步开始，客户和跨专业团队共同调整信息架构、布局、功能和视觉。
- 半成品页面中某些模式可能成熟而其他模式仍粗糙；滚动更新优于一次性“大揭幕”。
- 完整静态稿仍可在方向明确后显示整体，但应视为假设；动态数据、交互、性能和设备问题需在浏览器中决定。
- 组件成熟后，所有引用它的模板同步成熟，新模板逐渐变为组合既有模式。

## 第五章　维护设计系统（字符 189674—249470）

### 系统优先与重新定义“完成”

- 静态风格指南可能迅速失效；设计系统需要持续经费、路线图、待办事项、维护和支持。
- 应用层发现的问题需上升到系统层判断，例如某页面下拉菜单表现不佳，应检查同一模式是否全局修改。
- 设计系统不是有终点的项目，而是服务其他产品、长期演化的产品。

### 正式化路径

- 作者提出“做出东西—证明有用—转为正式项目”：
  1. 以试点建立可见模式库；
  2. 用项目经验和跨专业成员说明价值；
  3. 争取管理层批准、人员、预算、治理和路线图。
- “周末完成雏形”的建议反映草根策略，也可能掩盖无偿劳动，教材应作劳动史和组织史批评。

### 制作者与使用者

- 制作者负责创造、维护、审批和治理，掌握生态整体；
- 使用者把模式用于具体产品，提供现场反馈；
- 两者可能重叠，也可能分布于内部产品组、初级人员、合作机构和第三方。
- 大型组织可设专职团队，小型组织由资深且有执行权的成员兼任；外部顾问可提供启动和比较视角，但不能替代内部所有权。
- 跨专业不等于所有人持续编辑；用户体验、视觉和前端通常直接制作，后端、内容、产品和管理者提供约束与建议。

### 变更治理

- 治理需说明谁提出、批准、制作、记录、部署和通知变化，以及错误、新需求和退役模式如何处理。
- 修改原因包括功能、错误、视觉、性能、可访问性、重构和用户体验更新；
- 增加模式前需判断能否跨应用复用，避免无限膨胀；
- 删除模式应预告弃用并提供替代，避免破坏现有应用。
- Canonical Vanilla 的决策树和 Salesforce Sass Deprecate 分别示范接纳与弃用流程。

### “圣杯”同步与技术障碍

- 理想状态是模式库和生产应用共享单一来源，修改一处同时更新文档与产品。
- Lonely Planet Rizzo 通过模式 API 实现同步；CSS 和 JavaScript 可经版本化 CDN 分发，标记语言因与后端逻辑交织更难。
- Mustache、Handlebars、Twig、Underscore、Jade、Nunjucks 等模板语言可桥接模式库和 CMS；Phase2 以 Pattern Lab、Drupal 和 Twig 共享模板。
- 高度分散、多平台和自治组织未必适合完全中央同步。书中美国公共数字服务标准案例说明，可下载模式和文档也有治理价值。

### 跨专业、传播与培训

- 模式库应成为全组织共同资源。电商轮播同时涉及商品选择、文案、摄影、交互、响应式、可访问性、性能和后端。
- 指南需易看、易找、说明用途和受众；先保证系统有用，再逐步改善外壳。
- 传播方式包括内部博客、聊天频道、变更日志、路线图、成功案例、使用提示和自动通知。
- 培训包括结对、工作坊、网络讲座、教程和新员工入职；支持包括问题跟踪、办公时间、聊天、论坛和主动走访。
- 使用者可提交问题、建议和 pull request，参与访谈、圆桌、调查和状态会议。
- 作者主张公开指南以增加可达性、问责和招聘吸引力；这一判断需与安全、隐私和组织政策共同评估。

### 扩展、命名与情境

- 品牌、声音与语调、代码、设计原则、写作指南，以及 Web、iOS、Android 的共同和差异模式可集中于一个规范中心，如 Intuit Harmony。
- 名称应尽量依据结构而非页面或内容：`homepage carousel` 简化为 `carousel`，`product card` 简化为 `card`。
- 情境无关命名不等于取消情境。截图、视频、用法说明和模式谱系仍须解释组件何时、何地、如何使用。

- 作者先以日常困境或幽默故事建立问题，再给出术语、分类和操作步骤，最后用企业项目或从业者引语收束。

- 截图和代码不是附属插图，而是说明组件、状态、嵌套和工作流的证据载体；当前 Markdown 图片 OCR 不完整，引用时应回查原图。
- 章节逻辑从“为什么”到“是什么”“用什么”“如何做”“如何持续”，适合作为实践教材的结构样例。
- 语言具有强烈倡议和鼓动色彩，频繁使用“必须”“关键”“圣杯”“最佳实践”；历史教材应在保留行动者声音的同时区分主张、案例与经过验证的结论。

# 作者立场与可能局限

- Frost 站在 Web 前端设计师、开源工具开发者和咨询顾问立场，主张模块化、响应式、跨专业、活代码、公开分享与迭代治理。
- 叙事以北美和英语 Web 行业为中心，企业案例集中于 TechCrunch、Time Inc.、Salesforce、GE、Lonely Planet、Intuit 等；缺少非英语数字设计生态、公共资源差异和全球南方实践。
- 对效率、成本、质量、转化和用户信任的论断多为经验判断，缺少量化或比较验证。
- 对“先做后请示”、周末建立系统和系统团队附加责任的肯定，可能掩盖授权冲突、无偿劳动和组织权力。
- 对集中化、单一来源和统一规范总体持正面立场，对地方差异、抵抗、替代实践和系统失败讨论较少。

- 性别、种族、阶级和殖民结构几乎不构成正文分析维度；教材不能把这一缺席继续复制到数字设计史。
- 2016 年技术现场已发生变化，容器查询、前端框架、Pattern Lab、模板工具和组织案例都需版本化核查。
